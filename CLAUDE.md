# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A [Local](https://localwp.com) (by WP Engine) WordPress site named **auclair**. `app/public` is a stock WordPress core checkout (currently unmodified — default themes only, no custom theme or plugin has been built yet). `conf/` and `logs/` are Local's generated server config/logs and are not meant to be edited by hand — they're regenerated by the Local app (`*.hbs` files are Handlebars templates Local fills in).

The actual product work for this project lives in **`sites-template/`**, which is the build plan for an "AuClair Help Center" — a WordPress knowledge-base/support site — reverse-engineered from an HTML prototype (`Help Center.dc.html`, not in this repo). Nothing in `sites-template/` is executable; it's the spec to build the theme/plugin against. See `sites-template/wordpress/00-overview.md` for the file map.

## Running the site

The server (nginx, PHP-FPM, MySQL) is managed by the **Local app GUI**, not the CLI — start/stop the site from Local. `app/.envrc` is auto-generated by Local each time the site starts and points `wp`, `mysql`, and `php` at Local's bundled binaries; it's regenerated, don't hand-edit it.

Once the site is running and the Local-provided shell/env is active:
```bash
wp <command>              # WP-CLI, scoped to this site's DB via Local's env
wp plugin list
wp theme list
```
A generic `wp` on `$PATH` outside Local's shell (e.g. Homebrew's) will not point at this site's database — check `which wp` / `app/.envrc` before trusting output.

There is no build step, package manager, linter, or test suite configured in this repo yet (no `composer.json`, `package.json`, or `phpunit.xml` at the theme/plugin level). If you add a custom theme or plugin under `app/public/wp-content/`, set up its own tooling there and document the commands here.

## Architecture: the planned Help Center build

`sites-template/wordpress/` is the authoritative plan. Read `00-overview.md` first — it links the rest and sets stack assumptions:
- Block theme (FSE / `theme.json`), custom blocks under `auclair/` namespace, registered via `register_block_type` from `/blocks/<name>/block.json`.
- Text domain `auclair`.
- Dynamic blocks (PHP `render.php`) for anything reading posts/terms; static blocks for pure layout.
- Interactivity (search, dropdowns, hover ring, vote, file picker) via `@wordpress/interactivity` — no jQuery.
- ACF Pro (or native meta + block bindings) for the field groups defined in `post-types.md`.

Key docs and what they own:
| File | Defines |
|---|---|
| `post-types.md` | `kb_article`, `support_ticket`, `help_promo`, `kb_glossary` — fields, REST endpoints, and the admin-list voting/columns behaviour for articles |
| `taxonomies.md` | `help_category` (+ term meta: icon/accent/short_description/order/in_ticket_form), `help_tag`, `ticket_status`, `ticket_priority`, `platform`, `audience` |
| `blocks.md` | Every `auclair/*` block (S = static, D = dynamic, I = has an Interactivity store), plus shared behaviours (`ring-hover`, `accent-glow`, `focus-ring`) to implement once and reuse |
| `pages/0N-*.md` | Per-screen composition (block order), data source per section, interactions, and the ≤720px responsive changes |
| `coverage.md` | Element-by-element audit mapping every piece of the HTML prototype to a block/field, plus a list of behaviours *not yet decided* (search results page, real vs. hand-written article counts, ticket reference numbers, 404/empty states) |

When implementing part of this plan, cross-check `coverage.md`'s "Behaviour not yet in the prototype" section before inventing new UX — those are open questions, not settled.

### Design tokens (from `00-overview.md`, → `theme.json`)
- Dark palette: background `#101820`, surface `#131C24`, foreground `#F1F0ED`/`#ADAFAF`, border `rgba(241,240,237,0.08)`, single accent `#0075FF`; each `help_category` term carries its own accent via term meta.
- Type: self-hosted Satoshi (woff2), weights 500/700.
- Single responsive breakpoint at **720px** (above = desktop, at/below = mobile).
- Logo bar and hero are always full-bleed; other sections are centered (1120px max on landing, 720px max on category/article/ticket pages).

### Article feedback (most stateful piece of the plan)
`auclair/article-feedback` posts to `POST auclair/v1/vote` (`{ id, value: up|down }`). The endpoint nonce-checks, blocks repeat votes via a per-article cookie + IP transient, updates `vote_up`/`vote_down` post meta, recomputes `vote_score`, stamps `vote_last`. These are `register_post_meta` with `show_in_rest`, `type: integer`, `auth_callback` restricted to the endpoint. The article admin list (`edit.php?post_type=kb_article`) surfaces this via custom sortable columns (`manage_kb_article_posts_columns`, `pre_get_posts` meta-sort) — see `post-types.md` for the full hook list.
